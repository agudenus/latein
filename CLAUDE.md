This file provides guidance to Claude Code when working with code in this repository.

## Project Overview

**Polymarket Arbitrage Finder** — a tool that scans Polymarket (a prediction market platform) to detect and surface arbitrage opportunities.

The core idea: prediction market prices represent implied probabilities. When related outcomes are mispriced relative to each other (e.g. the YES/NO prices of a binary market sum to less than $1.00, or mutually exclusive outcomes across a multi-outcome event sum to less than 100%), a risk-free or low-risk profit opportunity exists. This tool finds those situations.

## Current Status

**Phase A complete and soaking.** The dry-run scanner (M1–M8: ingestion, detectors, cost model, daemon, packaging, WebSocket streaming, read-only dashboard, maker-fill simulation) is built, tested, and running on the owner's machine collecting go/no-go evidence. Phase B (execution/live trading) is designed but NOT built — it requires an explicit owner decision after the soak review. **M8 is the measurement that decision turns on**: it converts the report's hypothetical maker P&L (an upper bound — it assumes every resting leg is crossed) into a defensible *lower* bound by simulating resting orders last in their queue against observed trade prints, with **zero orders placed and still no wallet, key or signing code in the binary**. The report now shows all three numbers apart: `lower bound ≤ truth ≤ hypothetical`. The research below informed the architecture and remains the strategy source of truth.

Research collected so far lives in `research/`:
- `awesome-prediction-market-tools.md` — survey of the prediction-market tool ecosystem: existing arbitrage tools (competitive landscape), data/API providers, and open-source projects worth studying (Polymarket JB Bot, PMXT, TREMOR, pykalshi).
- `arbitrage-analysis-polymarket-nba.md` — summary of arXiv:2605.00864 (UCLA): single-market YES/NO arbitrage is nearly extinct (7 episodes, ~3.6s median); combinatorial arbitrage between logically dependent markets (moneyline vs. spread) is the real opportunity (~101 bps median) but is depth-constrained to retail size. Key design consequences: depth-aware profit math is mandatory, and cross-market logical-dependency detection matters more than single-market scanning.
- `polymarket-paradox-manipulation-whales.md` — summary of SSRN 6670638 (Abid, full PDF read): Polymarket is accurate on average but exposed to whale price impact (single trader moved the 2024 election market 10–15 points vs. other venues for three weeks, un-arbitraged) and oracle/governance capture (UMA disputes settled $250M+ of markets controversially, one against ground truth). Key design consequences: cross-platform divergence is not automatically arbitrage; resolution risk must be flagged per market; intra-Polymarket combinatorial arbitrage is more robust than cross-platform; liquidity must be measured from order book depth, never reported volume (volume is double-counted and was up to ~60% wash trading).
- `execution-costs-and-arb-filtering.md` — practitioner guide (owner-provided): most detected gaps die to bid-ask spread (a tick study found 90% "arbitrage" collapses to 24.5% once spreads are counted), then to Polymarket's taker fee curve (`rate × p × (1−p)`, peaking at 50/50 exactly where gaps cluster; makers pay zero), and much of the rest is relative value mislabeled as arb. Key design consequences: compute gaps on executable book sides (never mid/last); apply a per-category fee model to every opportunity; label true-arb vs relative-value; report net-after-costs at executable size, as taker and as maker; prefer maker-side capture (with legging risk handled). Fee rates verified against official docs 2026-07: geopolitics 0 (fee-free), politics/finance/tech/mentions 0.04, sports/economics/culture/weather/other 0.05, crypto 0.07.
- `market-opportunity-and-strategy-report.md` — deep-research synthesis (adversarially verified, 2026-07): realized-arb evidence (AFT 2025, ~$40M/yr) shows NegRisk multi-outcome rebalancing is ~72% of realized profit and combinatorial only ~0.24%; maker capture is positively subsidized (zero fees + rebates + daily liquidity rewards with API-queryable qualification params). **MVP focus decision: intra-Polymarket NegRisk rebalancing (politics first), secondary single-condition YES/NO rebalancing in sports, opportunistic fee-free geopolitics; combinatorial and cross-platform deprioritized.**
- `short-duration-crypto-bot-architecture.md` — practitioner architecture guide (owner-provided) for BTC Up/Down 5m-style markets: the decision chain (data → signal → fair value → executable edge → position structure → execution → risk), five position structures (temporal arb, hedged directional, inventory MM, near-resolution capture, rotation), execution detail (legging policy, reservation pricing, order types, post-only, size-splitting), and risk framework (fractional Kelly + hard caps + kill switch). Crypto is the highest-fee tier and latency-sensitive — not the MVP, but the execution/risk patterns apply to our chosen focus.

## Domain Context

Key concepts Claude should know when working here:

- **Polymarket** is a crypto-based prediction market on Polygon. Markets resolve via UMA oracle. Outcome shares trade between $0.00 and $1.00 and pay out $1.00 if correct.
- **Binary markets**: YES + NO shares. If YES + NO ask prices sum < $1.00, buying both locks in profit at resolution.
- **Multi-outcome (negative-risk) events**: mutually exclusive outcomes. If the sum of all YES prices < $1.00 (or NO-side equivalents > threshold), arbitrage may exist.
- **CLOB API**: Polymarket runs a central limit order book. Public REST/WebSocket APIs expose markets, order books, and prices (see https://docs.polymarket.com).
- **Practical frictions** that any arbitrage math must account for: order book depth/slippage, gas/transaction fees, resolution risk, capital lockup until resolution, and API rate limits.

## Planned Scope

1. **Market data ingestion** — fetch markets and order books from Polymarket's public APIs.
2. **Arbitrage detection** — scan for intra-market (YES/NO sum), cross-outcome (negative-risk), and combinatorial mispricings, filtered through the execution-cost model in `research/execution-costs-and-arb-filtering.md`.
3. **Opportunity reporting** — surface opportunities with expected profit, required capital, depth-adjusted sizing, and risk notes. Includes the read-only web dashboard (M7): monitoring only, never a control surface.
4. **Execution** — the owner has explicitly requested trading automation (2026-07): the bot will trade detected arbs with a dedicated wallet funded by the owner. Execution must ship behind a dry-run mode first, with per-trade and total exposure caps, and live trading only enabled by an explicit config flag.

## Wallet & Security Rules (non-negotiable)

- The trading wallet is a **dedicated hot wallet funded only with capital the owner can afford to lose** — never a main wallet.
- Private keys and API credentials live **only in environment variables / deployment secrets** (`.env` is gitignored). Never in code, config files, logs, chat, or commits.
- Every execution path must respect: max order size, max total exposure, max open positions, and a global kill switch.
- Default mode is **dry-run** (log intended orders, don't send). Live mode requires an explicit opt-in flag.

## Codebase Layout

Rust binary crate `polyarb` (Phase A: scanner + dry-run only; no wallet/key code exists).

- `src/main.rs` — CLI: `markets` (universe discovery), `scan` (one-shot detection), `run` (dry-run daemon; refuses any mode other than `dry-run`), `report [--date]` (daily summary), `dashboard` (M7 read-only web monitor).
- `src/gamma.rs` / `src/clob.rs` / `src/http.rs` — Gamma `/events` discovery, CLOB batch book fetch, shared throttled/retrying transport. The reqwest client carries **two** ceilings (M7.1): `api.request_timeout_secs` for the whole request and `api.connect_timeout_secs` (10 s) for DNS+TCP+TLS alone, because it was the connect phase that stretched a loop tick to minutes during a live DNS outage. The live `/events/keyset` envelope (`{$schema, events[], next_cursor}`, verified 2026-07-30) is parsed alongside the legacy bare-array and `{data}` shapes; a discovery pass that yields zero events is an `ApiError::EmptyDiscovery` naming the count and the endpoint, never a silent empty universe.
- `src/types.rs` — Decimal-only domain types (**no f64 in any money path — enforced convention**), including `MarketFees` (Gamma's per-market `feesEnabled`/`feeType`/`feeSchedule`).
- `src/costs.rs` — verified fee curve + cost decomposition (`net_maker = gross_gap + spread_cost` identity). `breakdown` takes **one taker rate per leg**; `FeeModel::resolve` prefers the market's API-stated rate (`feesEnabled=false` ⇒ 0; `feeSchedule.rate` with exponent 1 ⇒ that rate) and falls back to the category table when the API says nothing or states a formula this build does not implement (counted, and warned once per refresh).
- `src/detect.rs` — binary, NegRisk YES-side, NegRisk NO-side detectors; depth-walked joint sizing. `ScanCounters` (M7) counts the two funnel stages that leave no row behind: constructions whose executable ask sum was under the payout, and those still net-positive as a taker at the smallest tradeable size (pre-floor).
- `src/makersim.rs` — **M8, the maker-fill simulator**: the daily report's hypothetical maker P&L (which assumes every resting leg is crossed) turned into a defensible **lower bound**, with zero orders placed. When a maker-only opportunity is detected it records the resting buy each leg implies — at `leg.best_bid`, the exact price `net_maker = payout − Σ best_bid` is computed from — plus `Q0`, the size visible at that price at that instant. A leg fills only once subsequent **SELL** trade prints at or *through* our price total `Q0 + our_size`: last in queue, the level fully traded through, then us. Cancels ahead of us are never credited (invisible in public data), a book improving without prints is not a fill, an unreadable print is not evidence, and partial fills do not exist (a leg is filled or it is not). Verdicts — `maker_filled` (credits `net_maker_total`) / `maker_partial` (credits nothing, records the filled legs' cost as legging exposure) / `maker_unfilled` / `maker_untracked` (evicted at `maker_sim.max_concurrent`, oldest first — a *missing* measurement, never a non-fill) — are written once and never revised. Prints arrive through a `ws::PrintObserver` installed on the stream's `BookStore`, indexed by asset so a print costs O(sims on that asset) across a 147k-token feed; SQLite writes stay on the daemon loop. In REST-only fallback there are no prints, so those windows close `maker_unfilled` carrying `no_print_feed` — a hole in the measurement, reported as such. What it still cannot see, and the report says so: **our own order would itself have changed the queue**, and the 1 h window is longer than a live quote would ever rest.
- `src/risk.rs` — per-trade cap (Phase A scope).
- `src/store.rs` — SQLite persistence; money stored as TEXT Decimal strings, never REAL. Migration **v4** (M8) adds `maker_sims`: one row per **closed** simulation only (an in-flight one has no verdict, and a row that could be revised is not evidence), carrying the per-leg placement snapshot as JSON — price, size visible ahead of us, our size, fill state, prints observed — so a verdict is re-derivable and a later run could re-score the same soak under a different queue assumption. `pnl_lower_bound` is NULL except on `maker_filled` and `legging_exposure` NULL except on `maker_partial`: "not applicable" and "zero" are different facts. Migration v3 (M7) adds `runtime_status` (single-row JSON of daemon-memory state, republished every ~5 s) and `scan_stats.gaps_detected` / `.fee_survivors`, plus `Store::open_read_only` (`SQLITE_OPEN_READ_ONLY` + `PRAGMA query_only`, never migrates).
- `src/ws.rs` — M6 streaming market data: CLOB WebSocket market channel, sharded connection pool, defensively parsed frames, locally maintained books with staleness/resync, debounced dirty-event detection. Every wire shape is `TODO(verify-live)` (the container cannot reach the endpoint). M6.1: staleness comes from explicit invalidation or a *shard disconnect*, never from silence (quiet ≠ stale); the REST-only fallback requires WS failing **while REST demonstrably works** (both down = network outage = retry both forever) and is re-probed every `stream.reprobe_interval_secs` so it lasts only until the socket proves itself again. **M6.5** (verified live wire format, 2026-07-30): the delta frame is `price_changes[]` with a **per-entry `asset_id`** (one frame may touch several assets of one market; `BUY`=bid side, `SELL`=ask side, size `0` removes the level, parent `timestamp` dates every entry) — the old `changes[]` / single-top-level-change shapes stay as fallbacks. The first soak read 4.8M frames and applied **zero** deltas against this bug, so diagnosability shipped with the fix: `frames_unrecognized`, `delta_entries_applied` / `delta_entries_skipped` and `delta_top_mismatch` (an entry's own `best_bid`/`best_ask` vs the book we built — counted, never resynced on) are on the data-plane health line, and the first `UNRECOGNIZED_SAMPLE_LIMIT` (3) unusable payloads are logged **raw** at WARN (truncated to 500 chars; public market data) so the next shape drift names itself. **M7.1**: those three samples turned out to be `last_trade_price` frames — legitimate trade prints — so they now parse to `MarketFrame::TradePrint`, counted as `trade_prints` and applied to no book (a print says what traded, the book holds what is resting); `frames_unrecognized` is left meaning only "the wire format drifted". `connect_async` also gets a 15 s `CONNECT_TIMEOUT_SECS`, without which a shard whose DNS never answers is stranded silently: no connection, no recorded failure, no streak, no fallback decision. **M8** gives the print a *reader* without giving it a book: `MarketFrame::TradePrint` now carries `price`/`size`/`side`/`transaction_hash`, a `TradeSide` enum keeps the trade vocabulary apart from the book's `Side` (`SELL` = the aggressor sold into the bid side), `trade_prints_usable` counts the subset with a token, price and size, and an optional `PrintObserver` on the `BookStore` hands each print to the maker simulator — still applied to no book.
- `src/dryrun.rs` — daemon loop (REST-timer *and* stream-triggered detection through one shared `process_opportunities` path), opportunity lifecycle (filled_simulated vs vanished decided by first re-poll, never revised), daily summaries incl. detection-latency p50/p95. **M7.1** separates two questions that one timestamp used to conflate: a `Heartbeat` task republishes `runtime_status` on its own ~5 s timer (so a stale row means *the process is gone*, never "the loop is busy"), while `LoopProgress` — updated on every finished unit of work, including each `/books` batch — says whether the loop is moving. A progress watchdog exits with `WATCHDOG_EXIT_CODE` (75) after `daemon.watchdog_stall_secs` of no progress, naming the phase it stopped in, so a restart policy revives a clean process; it is **unarmed until the first unit of work completes**, so the long first discovery-and-seed can never look like a wedge. This exists because a DNS outage stretched a tick to minutes: the dashboard reported "daemon stopped reporting" about a working daemon, and nothing restarted the two hours of degradation that followed. **M8** adds the maker-sim lifecycle to the same loop: a simulation is opened for every *new* maker-only row (one per row, so a re-detection at the same quotes does not post a second phantom order), expired and persisted on the timer tick, closed where it stands when its event leaves the universe, and closed out at shutdown. The daily summary gains a `## Maker fills (simulated, last-in-queue)` section and a third P&L number that is never merged with the other two — the report now states `lower bound ≤ truth ≤ hypothetical` in one sentence.
- `src/alert.rs` — Telegram send-only alerts with JSONL fallback + circuit breaker; token never logged. M6.1 adds an alert-level cooldown per `(event, kind, side)` (row-level dedupe unchanged — different economics is still its own measurement row; only the *message* is held back, and it is still logged with `delivery = "cooldown"`).
- `src/dashboard/` — **M7 read-only web monitor** (`state.rs` derives one JSON snapshot from SQLite; `render.rs` server-renders it; `assets/` holds the vendored Nocturne stylesheet, the component CSS and a small vanilla poll script, all `include_str!`'d so the binary is self-contained). A **separate process** from the daemon: no shared state, `GET` routes only (`/`, `/api/state`, `/assets/*`), no button/form/POST anywhere, and a test enumerates the routes to keep it that way. Money crosses the JSON boundary as Decimal **strings**, never numbers, and is never parsed back in JS. The break state (design `2d`) takes the page over when the scanner is *blind rather than idle* — EmptyDiscovery, both transports down, all books stale, a missing/stale `runtime_status`, or (M7.1) a **stalled loop**: heartbeat current but no loop progress for `dashboard.loop_stall_secs` (300 s, half the watchdog's threshold so the stall is visible before the restart). That state keeps the real transport pill rather than claiming BLIND, because the shard counts come live from the pool. Deliberately **not** a takeover: a quiet socket, a fee-model fallback, an alert cooldown, an honest REST fallback, or a *slow* loop (a 195 s REST sweep reports progress on every batch). The funnel's "survive bid–ask spread" stage renders as *not instrumented* because gaps are computed on executable sides from the start, so there is no pre-spread population to filter. **M8**: the hero's maker stat shows the simulated **lower bound** with the hypothetical beside it (`sim lower bound (last in queue)` vs `if always filled`, never one number), and the rail gains `Maker sims: n open · fill rate x%` — the open count from `runtime_status` (in-flight sims exist only in daemon memory), the rate from the window's closed rows, with `maker_untracked` in neither part of it. `DASHBOARD_MIN_SCHEMA` is now v4.
- `config/default.toml` — all knobs, including `[stream]` (enabled by default), `[dashboard]` (loopback bind, poll cadence, evidence window) and `[maker_sim]` (M8: `enabled`, `window_secs` = 3600, `max_concurrent` = 200); secrets only via env (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`). `scan.activity_floor.min_liquidity_usd` was raised **$100 → $500** (M7.1): at $100 a live pass kept 73 450 markets / 146 900 tokens / 294 WS shards and a full REST sweep took 195 s, which is past what the owner's machine sweeps comfortably. An explicit value in an existing config keeps its own behaviour — only the default moved.
- `tests/fixtures/` — recorded API-shape fixtures (live Polymarket APIs unreachable from dev container; `TODO(verify-live)` markers track unverified API shape assumptions).

Quality gate for every change: `cargo build && cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --check`.
